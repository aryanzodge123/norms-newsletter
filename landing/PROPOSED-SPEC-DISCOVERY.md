# Proposed spec addition: how the page is read by machines

**Status: a proposal. It governs nothing.** Under CLAUDE.md rule 1 this should
have been written and approved before the code it describes. `PROPOSED-SPEC.md`
in this directory opens the same way, for the same reason, about the waiting
list.

That file and this one split `landing/`'s spec debt along a clean line. Its
subject is a table of other people's email addresses. This one's subject is
what a machine sees when it fetches the page, which is a smaller thing, but it
is the half that decides whether anybody finds the product at all.

---

## What exists today

The page serves no content. Measured on 2026-08-24:

```
$ curl -s https://norm.news/ | sed -n '/<body/,/<\/body>/p'
  <body>
    <div id="root"></div>
  </body>

$ curl -s https://norm.news/ | wc -c
    3166
```

Every word is written by React at runtime. The headline, the four benefit
blocks, the topic list, the delivery times, the footer, all of it arrives after
`src/main.jsx` executes. The served document contains no `<h1>`.

Google runs JavaScript, so this is not invisible to Google. It is invisible to
almost everything else: Bing, DuckDuckGo, every reader-mode and readability
parser, every link preview beyond the Open Graph tags, and every crawler that
feeds a language model. A page that cannot be read without a browser engine is
a page most readers of the web cannot read.

`sitemap.xml` and `llms.txt` both return 404. There is no structured data in
`landing/`, and none in `site/` either, so there is no in-repo precedent to
follow.

## Proposed: SPEC section 15, The landing page

SPEC.md ends at section 14 and nothing claims 15. The four subsections below
are what this proposal supplies. They are deliberately narrow, and the section
is not complete when they land. See *What this does not cover*.

### 15.1 What the page owes a machine

**The contract: a client that runs no JavaScript receives the whole page.**

Not a summary of it, not the Open Graph tags, not a fallback. The same words a
person reads, in the same order, in the response body.

This is the single requirement the rest of the section serves, and it is worth
stating as a contract rather than as a technique, because it survives a change
of framework. If `landing/` stops being React, 15.2 becomes wrong and this
stays true.

The page is one document at one URL. There is no router, no pagination, and no
second view. Anything that makes the page's content depend on a client-side
route breaks this contract and needs its own decision.

### 15.2 Prerendering

The page is rendered to static markup at build time and that markup is written
into the served HTML. Deterministic code, no model call, in keeping with rule
zero: this is a rendering step, and rendering is not something an AI touches.

**React re-renders over the markup rather than hydrating it.** The client entry
keeps `createRoot().render()`, which replaces the container's children. It does
not call `hydrateRoot()`. This is the load-bearing choice. Hydration requires
the server and client trees to agree, which turns every future edit into a
correctness problem and every mismatch into a runtime error. Replacing the
markup cannot mismatch, because nothing is compared. The prerendered copy exists
for readers that are not browsers, and the browser discards it within
milliseconds of the script loading.

The cost of that choice is that the markup is rendered twice, once at build and
once in the browser. For a page that is one screen of static copy, this is not
a cost worth optimizing.

**The build fails rather than shipping an empty page.** The prerender step
asserts that it found the root element and that the markup it produced exceeds
a floor, and exits non-zero otherwise. Silent degradation is the failure mode
that matters here: an empty root looks exactly like a working build until
somebody runs `curl` against production weeks later. That is how the current
state went unnoticed.

This is a build assertion rather than a test. `landing/` has no JavaScript test
runner and this proposal does not add one for a single script.

**Reduced motion and the no-JavaScript case.** Every element on the page starts
at `opacity: 0` and is revealed by script. Prerendering alone therefore
produces a document that is complete and invisible. A `<noscript>` rule
restores visibility, so a visitor without JavaScript reads a static document
instead of a blank screen. The page's interactive parts render in their initial
state and do nothing when operated. That is accepted: a readable page with inert
controls is better than no page.

### 15.3 The machine-readable surface

Four artifacts, all generated by the same build step, all derived from one
origin constant.

| Artifact | Contents |
| --- | --- |
| `robots.txt` | `Allow: /` and a `Sitemap:` directive |
| `sitemap.xml` | The one URL, with `lastmod` from the build |
| `llms.txt` | A plain-text summary of what the product is, composed from the page's own copy constants |
| JSON-LD | `Organization`, `WebSite`, and `SoftwareApplication`, in one `@graph` in the document head |

**`llms.txt` is generated from the page's copy, not written beside it.** A
hand-maintained summary of a page that changes is a summary that stops being
true, and nothing in the build would catch it. Composing it from the same
constants the components render means the two cannot disagree.

**Structured data describes only what exists.** No `AggregateRating`, no
`Offer`, no `Review`. The app is not released and has no users, so any of those
would be a fabrication, and fabricated structured data is specifically what
Google issues manual actions for. The temptation is real because the markup is
easy to write and the stars are visible in results. It is recorded here so that
adding them later is a decision somebody makes rather than a line somebody
slips in.

**One origin, one place.** Every self URL in these four artifacts derives from a
single constant in the build script. This is CLAUDE.md rule 6 applied to the
second front end: the site derives every self URL from `astro.config`, and a
hardcoded self URL there is a bug the milestone-verify gate fails. The same
reasoning applies here, and the pre-launch migration in section 13 is the
reason it will matter.

### 15.4 Crawler policy

**This subsection records a fact and decides nothing.**

`https://norm.news/robots.txt` returns 200 while no such file exists in
`landing/public/`. Cloudflare injects a managed robots.txt at the edge. As
served on 2026-08-24 it sets `Content-Signal: search=yes,ai-train=no,use=reference`
and disallows ClaudeBot, GPTBot, CCBot, Google-Extended, meta-externalagent,
Amazonbot, Applebot-Extended, Bytespider, and CloudflareBrowserRenderingCrawler.

Two things follow.

First, **the page's AI crawler policy was a Cloudflare default rather than a
decision.** Nobody chose it. It arrived with the zone. It was turned off in the
dashboard on 2026-08-24, which makes it a decision for the first time. The
served file is now the ten lines this build writes and nothing else.

Second, **it cannot be changed from this repository.** The managed block is
delimited by `# BEGIN Cloudflare Managed content` markers, which is how
Cloudflare merges its content into whatever file it finds at the origin.
Shipping a `robots.txt` does not remove those lines. The control is a dashboard
setting, and any `robots.txt` in `public/` has to be read as one half of the
served file.

The policy question is a product and rights question rather than an
engineering one, and it points both ways: the same block that keeps the page out
of training corpora also keeps it out of the retrieval systems that increasingly
answer "what should I read in the morning".

**It is answered for this page and open for the archive.** The landing page is
marketing for an unreleased app and carries no journalism, so being found is its
whole job and there is nothing on it worth withholding. That reasoning does not
transfer. If the published editions ever move onto this domain (see *What this
does not cover*), the same toggle would then govern real writing, and the answer
should be reached again rather than inherited. Section 11 carries that
remainder.

Note for the future: the user-initiated fetchers, `ChatGPT-User`, `Claude-User`
and `PerplexityBot`, are not on the block list. A person who pastes the link
into an assistant is served normally today. The block covers indexing and
training, not somebody asking about the page.

## Proposed decisions

For SPEC section 10, which currently ends at #56.

| # | Decision |
| --- | --- |
| 57 | The landing page is prerendered to static markup at build time, and the served HTML holds every word the page shows. React re-renders over that markup rather than hydrating it, so a server and client mismatch is impossible by construction rather than avoided by discipline. The build asserts the markup is present and fails otherwise, because the failure mode is silent: an empty root is indistinguishable from a working build without fetching production. The page shipped in that state and nobody noticed |
| 58 | Every self URL in the landing page's generated artifacts derives from one origin constant in its build script, the same way the site derives every self URL from `astro.config` under CLAUDE.md rule 6. A hardcoded self URL is a bug. The pre-launch migration in section 13 is what makes this worth enforcing on a page that today has exactly one URL |
| 59 | Structured data on the landing page describes only what exists. No `AggregateRating`, no `Offer`, no `Review` until there is a released app and real reviews to report. Fabricated review markup is what search engines issue manual penalties for, and the markup is easy enough to write that the rule has to be explicit rather than assumed |

Under the non-app-layer questions:

## What this does not cover

Recorded so that section 15 landing is not read as closing rule 1's gap for
`landing/`.

- **The page's visual system.** CLAUDE.md lists the app's visual system under
  *Not yet specified*, and DESIGN.md is the site's design system. Nothing here
  changes that.
- **The copy claims.** `README.md` records three things on the page that the
  spec does not carry, including the hero's claim about tracked stories and the
  hourly collector figure. They stay flagged there and are untouched by this.
- **The waiting list.** That is `PROPOSED-SPEC.md`'s subject and its
  recommendation is to name the table in 14.12. Unchanged.
- **The published edition archive.** The site publishes real writing daily to
  GitHub Pages while the good domain serves one marketing page. Putting the
  archive on `norm.news` is the largest thing that could be done for discovery
  and it is not proposed here, because it touches rule 6 and section 13 and is
  a question about what the two front ends are, not about markup.

## What is deliberately absent

- **No hydration.** See 15.2. The alternative was considered and rejected on
  the grounds that it buys nothing for a static page and costs correctness on
  every future edit.
- **No prerendering service or third-party renderer.** The page is one screen
  of static copy. It renders in the build that already exists.
- **No keyword pages, no blog, no landing page variants.** Thin pages written
  for search engines are the technique this project's voice standard exists to
  prevent. If the domain needs more content it should get the archive, which is
  real writing that already exists.
- **No analytics or tag manager.** Nothing here needs one, and a third-party
  script would undo the only benefit of removing the font host.
